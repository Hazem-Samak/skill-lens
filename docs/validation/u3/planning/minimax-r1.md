BLOCKERS:
1. **location** — `docs/plans/2026-10-19-tui-u3-home.md` §"Home behavior and layout" items 5 & 7 and the acceptance bullet "selected row and agent changes reject late successes/errors" + "The app's accepted-message handlers provide the UI-thread refresh/report integration points" (Current state, line 44); `skill_lens/tui/session.py:208-243` (`request_view` → `self.invalidate_view(view)` at line 224, *before* the cache lookup), `skill_lens/tui/session.py:333-341` (`set_selected_key` invalidates "why"), `skill_lens/tui/app.py:306-332` (`if accepted: self._update_ui()` — rejections are silent).
   **problem** — the draft's serial Why queue has no liveness/re-issue rule, and the controller makes the naive design deadlock: (a) the controller holds **one** active request per view, so any new "why" request cancels the previous one; (b) `set_selected_key` (which the draft mandates on every selection change) cancels the in-flight "why" request; (c) the app notifies the UI **only for accepted** results, so a cancelled request produces a late `ViewReportComplete`/`ViewReportFailed` that the controller rejects (`active_requests` has no "why" → `accept_view_result` returns False) and the app swallows it. A Home queue that waits for an accepted callback therefore never advances after the first cursor move or agent change, and the draft's "Invalidate pending Home why work on selection/agent change" yields no marks at all. This is exactly the product behaviour the implementer would have to invent.
   **expected behaviour** — the draft must state (i) how the Home learns a request was cancelled (e.g. `app.py` forwards *both* accepted and rejected outcomes to the Home screen, and the Home re-issues that `(key, agent_id)` or re-drives the queue), and (ii) the restart/priority rule after a selection or agent change, plus the acceptance "after the user stops navigating, the selected row's per-agent mark appears within the same generation".
   **evidence** — controller probe: `request_view("why", ("keyB","claude"))` set the first request's event (`ev1.is_set() == True`); `set_selected_key("keyC")` set the second event and emptied `active_requests`; the late `accept_view_result` returned `False` and left `cache == {}` — so no callback would ever reach the Home.
2. **location** — draft item 5 ("Use a small serial queue for visible rows", "Reuse cached full `(generation, why, (key, agent_id))` results"); `skill_lens/core/snapshot.py:610-640`; `skill_lens/core/resolver.py:243-330, 780-812`; `skill_lens/tui/session.py:57, 226` (cache key = `(generation, view, arguments)`).
   **problem** — the Why request granularity is unspecified, and the literal reading (one request per visible row) is wrong by a factor of the number of same-named copies: a Why report is **name-wide** (it resolves the entry's lookup name and returns candidates for *every* copy of that name), while the controller cache key embeds the per-row key, so N same-named rows produce N byte-identical reports and N serial worker round-trips. For the 600-skill benchmark the draft requires, that is 600 dispatches instead of the number of distinct names. The draft never states which granularity applies nor pins the Why-call count in acceptance, so the implementer must choose — and the choice drives the measured agent-filter responsiveness the draft demands.
   **expected behaviour** — state "one Why request per distinct lookup name for the active agent; all rows sharing that name are marked from that single report; a row with no matching candidate shows the explicit unknown mark", and pin it in acceptance ("M distinct names among N visible rows ⇒ M Why calls; same-named copies show different per-copy states from one report").
   **evidence** — probe on a synthetic home with two same-named `deploy` copies: both rows' `snapshot_why(claude)` returned the *same* candidate set `{user copy ACTIVE, project copy SHADOWED}` and the same name-wide `headline=ACTIVE`; the shadowed row's own candidate was correctly `SHADOWED` and the broken symlink row's was `INVALID`, an agent that does not search the root gave `UNSEARCHED` — so candidate→row mapping by `installation.canonical_path` is sound, but the per-row cache key forces duplicate work. Measured: `snapshot_why` = **0.92 ms** on a 600-skill index (600 calls ≈ 0.55 s compute, plus 600 worker dispatches and redraws).

SUGGESTIONS:
- **Must-not-break, state it in the draft** — `tests/test_tui_app.py:988` and `:994` assert `isinstance(app.screen, PlaceholderHomeScreen)`. The draft's "the old placeholder type *may* remain as a compatibility alias if needed" is too weak: it is needed, and it must be an alias (or base class) of the new Home screen, not a separate class. Also keep `#status-text` / `#error-details` semantics, not just the IDs (`"Ready:"`, `"Scanning skills..."`, the refusal text without "Press r to retry", `"Error: Unexpected internal fault"`) — pinned at `tests/test_tui_app.py:186-189, 217, 265, 433, 554, 653, 847, 1115, 1191, 1253`.
- **Mark vocabulary collision** — `skill_lens/presentation/state.py` `STATE_MARK` uses `*` for ACTIVE and `x` for INVALID, the same glyphs the draft assigns to parse status ("`*` valid, `x` invalid"). In one table that is ambiguous (a valid+active row shows `*` twice; an invalid+INVALID row shows `x` twice). The draft's "display enough text/legend to distinguish marks" is the right instinct but too thin: specify a distinct resolution column with a text label (e.g. `active`/`shadow`) or a separate glyph set, and put the legend in the strip.
- **Cell-level updates, not table rebuilds** — measured on a 600-row `DataTable`: one full `clear()+add_rows()` ≈ **3.4 ms** (≈2 s for 600 rebuilds) versus a single `add_row` ≈ 0.03 ms and `update_cell` in microseconds. The draft should require late marks to be applied with `DataTable.update_cell(row_key, column, value)` (the canonical row key is exactly the `add_row(key=...)` key) and require the benchmark to measure it; otherwise a per-mark rebuild is the default outcome.
- **Restate one acceptance bullet** — "cached arguments cancel outstanding work" describes the hazard, not the desired behaviour: `request_view` cancels the in-flight request *even on a cache hit* (`session.py:224` precedes the cache lookup at `:226-228`). The desired rule is "the Home checks `get_cached_report` **before** requesting, so a cache hit never cancels in-flight work; the in-flight `(key, agent_id)` is never re-requested on redraw".
- **State the mark-clearing rule** — the draft is explicit for refresh ("successful refresh removes stale marks/caches") but silent for an *agent* change: already-applied marks computed for agent X must be dropped when the filter switches to agent Y, otherwise the table shows agent X's states under agent Y's label. Add: "on agent change, all per-agent marks and pending state are cleared before the new agent's requests start."
- **Reuse the existing no-live-read harness** — `tests/test_session_snapshot.py:605` (`test_navigation_has_no_filesystem_fallback`) already installs a `forbid` sentinel over `discover`, `live_discovery`, `load_registry`, `os.walk/listdir/stat/scandir`, `Path.open/read_bytes/read_text/stat/resolve/iterdir` and `builtins.open`. Name it in the draft so the U3 "no filesystem reads on first filter/navigation visit" acceptance is provable rather than asserted.
- **Reuse the variant rule** — the preview's variant label must come from the captured `ScanEntry.variant_label` (`core/scanner.py:191`, shared `labels_for_entries`), never from the Why report's `installation.variant_label` (`core/resolver.py:661-679, 697-706`), which labels only the candidate subset and can drift (F-16 class). Say so explicitly.
- **Coverage headroom** — the combined total is 91.11% against a 90.00% floor (`[tool.coverage.report] fail_under = 90`, `pyproject.toml:90`), i.e. roughly one point of slack for the whole package. A large new `skill_lens/tui/home.py` with weak coverage can break the gate on its own; require the new module's own coverage to be reported in the walkthrough and keep the combined total ≥ the current 91.11% where practical.
- **Key-handling facts worth recording** (verified in a headless probe, so the implementer does not build a custom key filter): Textual 8.2.8's `Input.check_consume_key` (`widgets/_input.py:498-510`) removes printable keys from the binding chain, so `q/r/a/j/k` are plain text while the filter has focus, and `Input._on_key` (`:743-754`) inserts them; `ctrl+c` is *not* printable, so the app-level `ctrl+c → quit` still fires from any focus (confirmed: quit recorded with the Input focused). `DataTable` binds `enter/up/down/left/right/pageup/pagedown/home/end` and **not** `j/k` (`widgets/_data_table.py:273-285`), so screen-level `j/k` work; but `enter` on the table is `select_cursor` — U3 must leave it inert (no detail screen) per the draft's "do not advertise Enter-detail".
- **Escape needs an explicit action** — Textual 8.2.8's `Input` has no `escape` binding and does not clear itself (verified: the value survived and focus stayed on the Input), so "Escape clears the query and returns focus to the list" needs an explicit `input.value = ""` + focus move; note that setting `.value` re-fires `Input.Changed`, so the filter must not recurse.
- **Benchmark placement follows precedent** — `docs/validation/u1/benchmark_capture.py` and `docs/validation/u2/run_mutations.py` already establish the pattern; `docs/` is linted by `ruff check .` (no `exclude` in `pyproject.toml`) but is *not* pytest-collected (`testpaths = ["tests"]`) and is *not* covered by the AST read-only guard, which scans only `skill_lens/tui/` (`tests/test_tui_read_only.py:37, 351-356`). The new `skill_lens/tui/home.py` **will** be scanned by that guard, so it must avoid `open(...)` with any mode, `Path.write_*`/`unlink`/`mkdir`/`touch`/`rename`/`rmdir`/`chmod`/`symlink_to`, `os.remove/unlink/rmdir/rename/replace/chmod/system/popen`, `print(...)`, and any `rich` or `skill_lens.render` import.
